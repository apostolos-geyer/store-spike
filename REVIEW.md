### F1. Sweep-initiated expiry double-restores stock: the resulting expired webhook is not treated as late

**CRITICAL** · `src/Domain/Settlement.ts:224` · lens `?` · reviewer confidence `high`

**Defect.** The late-event guard treats `cancelled` as terminal only against SETTLING events, never against FAILING ones, so the `checkout.session.expired` webhook that Stripe emits in response to the sweep's own `payments.expire()` call restores the order's stock a second time.

**Failure.** Order SO-ABC holds 3 units of variant V (product P, preorder, quantity 3). Its session expires unpaid. The 15-minute cron runs `Reconcile.sweep`: the order matches the stale-attached query (sessionId set, status `pending`, paymentStatus `unpaid`, sessionExpiresAt < now); `retrieve` returns status `open`; `payments.expire(session.id)` succeeds; `release(order.id)` runs `restoreStatements` — variant V stock += 3, product P `preorder_claimed` -= 3 — and sets status `cancelled`, paymentStatus untouched (`unpaid`). Stripe then delivers `checkout.session.expired` (a forwarded event — src/Infrastructure/StripeDev.ts:53) with a fresh event id, so the `payment_event` replay key does not match and `settle` proceeds. It finds the order by sessionId; `order.status === "cancelled"`, `failing === true`; `alreadyTerminal` evaluates `TERMINAL.has("cancelled")` = false, `(failing && order.status === "paid")` = false, `(settling && ...)` = false, so the guard does NOT fire. Execution falls through to the FAILED branch at Settlement.ts:391 and runs `restoreStatements` again: variant V stock += 3 a second time (3 units of phantom inventory that will be sold to a buyer and never shipped) and `preorder_claimed` -= 3 again (the run is now oversubscribed by 3 places against a fixed manufacturing quantity). This is not a race — it happens deterministically for every order the sweep releases via the `open` → `expire` path.

**Independent verification.** I traced this end to end and it holds. Reconcile.release (src/Domain/Reconcile.ts:68-79) writes only `{status: "cancelled", updatedAt}` — paymentStatus is left at `unpaid` — after `restoreStatements` has already put the units and the run place back. It is invoked at Reconcile.ts:175 on the fall-through from the `session.status === "open"` branch (Reconcile.ts:164-173) i.e. immediately after the sweep itself calls `payments.expire(session.id)` (PaymentsStripe.ts:259-265 → `stripe.checkout.sessions.expire`). Stripe emits `checkout.session.expired` in response to that API call, and that event type is on the forwarded/subscribed list (src/Infrastructure/StripeDev.ts:53). It carries a fresh event id, so the `payment_event` replay lookup at Settlement.ts:99-106 misses. The order is still found by sessionId (Settlement.ts:159-167; the sweep never clears sessionId). At Settlement.ts:221-225 `alreadyTerminal` = !reversing && (TERMINAL.has("cancelled") — false, since TERMINAL is only {shipped, delivered} at line 78 — || (failing && status==="paid") — false || (settling && status==="cancelled") — false because settling is false for an expired event) ⇒ false. reversing false, `paid` false, `settling && !paid` false, so control reaches the FAILED branch at Settlement.ts:391-416, which re-selects every order_item row and runs `restoreStatements` a second time. `restoreStatements` (Reservations.ts:334-368) is an unconditional relative `stock + qty` plus `max(0, preorder_claimed - qty)` — no guard on order status, no idempotency marker. Net: variant stock is credited twice (phantom inventory that oversells) and preorder_claimed is decremented twice (run oversubscribed). The stale-attached query (Reconcile.ts:102-114) requires status='pending', so the sweep itself won't re-pick the order — nothing downstream corrects this. The file docstring at Settlement.ts:20-22 explicitly claims the 'vice versa' case is handled; the guard does not implement it. Also reachable via the `session.status === "expired"` path when Stripe's earlier expired event is merely delayed rather than lost. No test covers sweep-release-then-expired (test/settlement.integ.test.ts S1-S8).


### F2. `cancelled` is not terminal against a FAILING event — the sweep's own expire causes a second stock restore

**CRITICAL** · `src/Domain/Settlement.ts:221` · lens `?` · reviewer confidence `high`

**Defect.** `TERMINAL` is only `{shipped, delivered}`, and the FAILING arm of the late-event guard only treats `paid` as terminal. An order already cancelled-and-restored is therefore still eligible for the failure branch, which restores stock a second time — and `Reconcile.sweep` deliberately creates that exact ordering by calling `payments.expire`, which makes Stripe emit `checkout.session.expired`.

**Failure.** Buyer abandons a 2-unit cart. 40 minutes later the cron sweep picks the order up (`status='pending'`, `paymentStatus='unpaid'`, `sessionExpiresAt < now`), Stripe still reports the session `open`, so the sweep calls `payments.expire(session.id)` (Reconcile.ts:165) and then `release()` — `stock += 2`, `preorder_claimed -= 2`, `status='cancelled'` (Reconcile.ts:70-78). Stripe now delivers `checkout.session.expired` for that same session. `settle` finds the order by `sessionId`; `alreadyTerminal` evaluates `TERMINAL.has('cancelled')` = false, `failing && 'cancelled' === 'paid'` = false, `settling && ...` = false, so the guard does not fire and control reaches Settlement.ts:391-416, which runs `restoreStatements` again: `stock += 2` a second time and `preorder_claimed -= 2` a second time. The variant now claims two units that do not physically exist and the pre-order run has two phantom places, so the next two buyers are sold goods that cannot ship.

**Independent verification.** Confirmed by tracing every guard on the path; nothing catches it.

`src/Domain/Settlement.ts:78` `TERMINAL = new Set(["shipped", "delivered"])`. `src/Domain/Settlement.ts:221-225`: for `checkout.session.expired`, `settling=false`, `failing=true`, `reversing=false`. With `order.status='cancelled'`: `TERMINAL.has('cancelled')`=false, `failing && status==='paid'`=false, `settling && status==='cancelled'`=false (settling is false). Guard does not fire.

The ordering is manufactured by the sweep itself: `src/Domain/Reconcile.ts:164-175` calls `payments.expire(session.id)` and, on success, `release(order.id)` — which at `src/Domain/Reconcile.ts:68-79` runs `restoreStatements` (stock += qty, preorder_claimed -= qty) and sets `status='cancelled'`. `src/Services/PaymentsStripe.ts:259-265` confirms this is `stripe.checkout.sessions.expire`, which makes Stripe emit `checkout.session.expired`. That event then reaches `src/Domain/Settlement.ts:391-416` and runs `restoreStatements` a SECOND time.

I checked for downstream correction and found none. The `payment_event` dedupe (`src/Domain/Settlement.ts:99-106`) keys on the provider event id, which is fresh. The lookup succeeds via `sessionId` (`src/Domain/Settlement.ts:159-167`) because `release()` never clears `session_id`. No schema guard stops it: `stock_non_negative` (`src/Domain/Schema.ts:270`) only blocks going below zero, `preorder_claimed_non_negative` is satisfied because `compensateRunStatement` uses `max(0, ...)` (`src/Domain/Reservations.ts:265`), and `preorder_claimed_within_cap` is satisfied by a decrement. `customer_order` has no status-transition CHECK (`src/Domain/Schema.ts:367-375`).

Outcome is exactly as described: `stock` inflated by the line quantity and `preorder_claimed` deflated by it, i.e. physical oversell plus phantom places in the run. Directly contradicts `src/Domain/Settlement.ts:20-22` and the terminal-status docstring at `src/Domain/Settlement.ts:70-77`. Critical stands.


### F3. A partial refund is settled as a full reversal: order cancelled, books show fully refunded, all stock returned

**CRITICAL** · `src/Domain/Settlement.ts:244` · lens `?` · reviewer confidence `high`

**Defect.** `charge.refunded` fires for partial refunds as well as full ones, but the reversal branch carries no amount at all — it unconditionally flags the order `refunded`, cancels it, and hands every line's stock back, and it is exempted from the late-event guard so a second partial refund restores the same stock a second time.

**Failure.** Order SO-ABC: 2 shirts, subtotal 5000, shipping 1200, tax 806, total 7006, status `paid`, not yet shipped. Support issues a 1000-cent goodwill refund in the Stripe dashboard. Stripe emits `charge.refunded` (it emits this for partial refunds too; the charge object has `refunded: false`, `amount_refunded: 1000`). settle() takes the `reversing` branch: `disputed` false, `gone` false, so it adds 2 units back to `product_variant.stock` (and a pre-order run place back), sets `status = 'cancelled'`, `paymentStatus = 'refunded'`. Outcome: the store's books say the whole 7006 came back and the order is dead, while Stripe kept 6006 — the refunded 1000 is recorded nowhere, and `totalCents` still reads 7006, so no report can reconcile. The customer's still-owed order now reads cancelled. Two units of inventory the customer is keeping are back on sale. Issue a second 1000-cent goodwill refund on the same charge and a new event id arrives, the reversal branch is reached again (it is exempt from `alreadyTerminal`, and `cancelled` is not in TERMINAL), and the same 2 units are added to stock a second time — 4 phantom units from a 2-unit order.

**Independent verification.** Traced and confirmed end to end. `REVERSING` includes `charge.refunded` (src/Domain/Settlement.ts:64) and that event type is explicitly subscribed (src/Infrastructure/StripeDev.ts:61), so the path is live. The adapter throws away every amount on a charge event: src/Services/PaymentsStripe.ts:302-323 returns `amounts: null` and reads only `payment_intent` — it never touches `amount_refunded`, `amount`, or `refunded`, and `ProviderEvent` (src/Services/Payments.ts:73-105) has no field that could carry a refunded amount even if it wanted to. Stripe emits `charge.refunded` for partial refunds as well as full ones, so the reversal branch at Settlement.ts:244-277 cannot distinguish them: it sets `paymentStatus: 'refunded'`, adds `status: 'cancelled'` whenever the order is not shipped/delivered, and runs `restoreStatements` over every order line. `restoreStatements` (src/Domain/Reservations.ts:334-344, 356-367) is a bare `stock = stock + qty` plus a `preorder_claimed` decrement with no idempotence and no guard. Nothing in the branch touches `subtotalCents/shippingCents/taxCents/totalCents`, so a 1000-cent goodwill refund on a 7006-cent order leaves `totalCents = 7006` with `paymentStatus = 'refunded'` and `status = 'cancelled'`.

I looked for the guard that would save it and it is not there. The late-event guard at Settlement.ts:221-225 is `!reversing && (...)`, so reversals are exempt outright; `cancelled` is not in `TERMINAL` (Settlement.ts:78) and `gone` at line 246 only tests `shipped`/`delivered`. A second partial refund therefore arrives with a new event id (not a `duplicate` at Settlement.ts:106), still resolves the order via `byIntent` (Settlement.ts:185-194, `paymentIntentId` is still set), and re-runs `restoreStatements` — 4 phantom units from a 2-unit order, exactly as claimed. Nothing downstream corrects any of this: `fulfillOrder` (src/Domain/Orders.ts:262) refuses `cancelled → shipped`, and `setOrderStatus` cannot move an order out of `cancelled` (TRANSITIONS at Orders.ts:42-48 has `cancelled: []`), so the order is permanently dead and the returned inventory is permanently on sale.


### F4. Every charge.refunded event restores the full order's stock, so partial refunds duplicate inventory

**HIGH** · `src/Domain/Settlement.ts:248` · lens `?` · reviewer confidence `high`

**Defect.** The REVERSING branch restores the entire order's line quantities on every `charge.refunded` event, but Stripe emits one `charge.refunded` per refund object on a charge (partial refunds included), and each has a distinct event id so the `payment_event` replay key never suppresses the second one.

**Failure.** Order SO-XYZ was paid: 4 units of variant V (product P, preorder). The customer is refunded $20 of the $200 order — Stripe fires `charge.refunded` (evt_1). `settle` matches the order by `paymentIntentId`; `reversing` is true so `alreadyTerminal` is forced false by construction; `disputed` false, `gone` false (status is `paid`); so all 4 units go back to variant V, `preorder_claimed` drops by 4, and the order is flipped to `cancelled`/`refunded` even though 90% of the money was kept. A week later the remaining $180 is refunded — Stripe fires `charge.refunded` again (evt_2, different id, so not a `duplicate`). The order is now `cancelled`, which `TERMINAL` does not contain and which the `gone` test (`shipped`/`delivered`) does not catch, so the branch runs a second time: variant V gains another 4 phantom units and `preorder_claimed` drops another 4, oversubscribing the run by 4 places. The store will sell 4 garments it cannot make and 4 units it does not have.

**Independent verification.** Confirmed. `charge.refunded` is in REVERSING (Settlement.ts:64) and is a subscribed/forwarded event (StripeDev.ts:61). Stripe emits one `charge.refunded` per refund object created against a charge, so N partial refunds produce N events with N distinct event ids — the replay lookup at Settlement.ts:99-106 keys on event id only and cannot collapse them. For the second event: the order is still found via `paymentIntentId` (Settlement.ts:185-194; paymentIntentId is never cleared by the first reversal at Settlement.ts:262-275, which only sets paymentStatus/status). `reversing` forces `alreadyTerminal` to false by construction (Settlement.ts:222, `!reversing && ...`). `disputed` is false; `gone` tests only `shipped`/`delivered` (Settlement.ts:246) and the first reversal set status to `cancelled`, which is neither — so `lines` is repopulated with the full order and `restoreStatements` runs again at Settlement.ts:264. Net: full-order stock credited once per refund event, and `preorder_claimed` decremented once per refund event. There is no partial-vs-full amount test anywhere (ProviderEvent carries no refund amount at all — PaymentsStripe.ts:302-322 maps charge events to sessionId/paymentStatus/amounts = null), and no 'already reversed' check. Test S8 (test/settlement.integ.test.ts:457) exercises a single refund only. The 'flip to cancelled/refunded on a 10% refund' half is a modelling gap rather than a defect per se; the duplicated `restoreStatements` on the second event is the concrete money loss.


### F5. Reversals skip the late-event guard, so each partial refund restores the whole order's stock again

**HIGH** · `src/Domain/Settlement.ts:244` · lens `?` · reviewer confidence `high`

**Defect.** `alreadyTerminal` is short-circuited by `!reversing`, and the reversal branch itself has no idempotence check beyond the per-event-id dedupe. Stripe emits one `charge.refunded` per refund on a charge, each with its own event id, so N partial refunds run `restoreStatements` over the order's full line set N times.

**Failure.** A paid 3-unit pre-order is refunded in two instalments (support refunds $40 today, the remaining $80 tomorrow). Refund #1: `charge.refunded` matches by `paymentIntentId`, `disputed`=false, `gone`=false (status `paid`), so all 3 units go back to `stock`, `preorder_claimed -= 3`, and the order is set `cancelled`/`refunded`. Refund #2 is a distinct event id so the `paymentEvent` dedupe misses; `reversing` is true so `alreadyTerminal` is forced false regardless of the order now being `cancelled`; `gone` is still false because `cancelled` is neither `shipped` nor `delivered`. The full 3 units are restored a second time. Inventory is inflated by 3 units and the pre-order run gives away 3 places that were never freed — the store oversells the next buyers on both counts.

**Independent verification.** Confirmed. Same defect class as the previous finding but a distinct code path with a distinct trigger.

`src/Domain/Settlement.ts:222` `!reversing &&` short-circuits the whole `alreadyTerminal` expression for `charge.refunded` / `charge.dispute.created` (`src/Domain/Settlement.ts:64`). The reversal branch at `src/Domain/Settlement.ts:244-277` has exactly two conditions gating the restore: `disputed` (event type prefix) and `gone = status === 'shipped' || status === 'delivered'`. After refund #1 the order is set `status='cancelled', paymentStatus='refunded'` (`src/Domain/Settlement.ts:266-272`), and `cancelled` satisfies neither condition, so refund #2 reloads the full `order_item` set (`src/Domain/Settlement.ts:248-260`) and runs `restoreStatements` over all of it again.

The only dedupe is the per-event-id check at `src/Domain/Settlement.ts:99-106`; Stripe fires a separate `charge.refunded` with a fresh event id for each refund created against a charge, so it misses. `paymentStatus='refunded'` is never read as a guard anywhere on this path. I checked the CHECK constraints (`src/Domain/Schema.ts:109-113`, `:270`) — a restore only increments stock and decrements `preorder_claimed` through `max(0, ...)`, so nothing aborts.

The author's own justification at `src/Domain/Settlement.ts:216-219` reasons only about shipped/delivered, and the code applies the exemption to repeated delivery of the same reversal too. Note the exemption is not needed for its stated purpose: `gone` at `src/Domain/Settlement.ts:246` already handles shipped/delivered independently of `alreadyTerminal`. High stands.


### F6. Queue consumer discards settle's outcome and pins attempt to 1 — `retryable` acks and drops the event

**HIGH** · `src/Workers/Settlement.ts:107` · lens `?` · reviewer confidence `high`

**Defect.** The consumer runs `settle(...)` with `discard: true` and never fails, so alchemy's EventSource acks every message in the batch; a `retryable` outcome is therefore acked and lost, not retried. `attempt` is hardcoded to 1 at enqueue and a Cloudflare retry redelivers the same body, so `attempt < MAX_ATTEMPTS` is always true and the `dead` row is never written on the deployed path.

**Failure.** An order was healed by the reconcile sweep (Reconcile.ts:141-148 sets only `status`/`paymentStatus` and never writes `paymentIntentId`), or was settled via the metadata path where `describesOurSession` was false — either way `customer_order.payment_intent_id` is NULL. The buyer then disputes. `charge.dispute.created` arrives as a charge event with `sessionId: null` and `orderId: null` (PaymentsStripe.ts:313-315), so the only lookup available is by payment intent and it matches nothing. `settle` takes `if (!order) { if (attempt < MAX_ATTEMPTS) return { outcome: "retryable" } }` with attempt fixed at 1 — returning **before** any `payment_event` row is written. The handler effect succeeds, alchemy calls `msg.ack()` on the whole batch, and the dispute vanishes: no `payment_event` row, no order update, `status` still `paid`. The operator sees a shippable paid order and ships goods against a charge that has already been pulled back, and the store has no record the event ever arrived.

**Independent verification.** Confirmed against the alchemy source, not just the call site.

`node_modules/alchemy/src/Cloudflare/Queues/EventSource.ts:239-259`: `process(...)` is piped through `Effect.tap(() => { for (const msg of batch.messages) msg.ack() })` on success, with `msg.retry()` only under `Effect.onError`. `src/Workers/Settlement.ts:103-112` runs `settle(...)` under `Effect.forEach(..., { concurrency: 1, discard: true })` and `settle`'s signature is `Effect.fn.Return<Settlement, never, Database>` (`src/Domain/Settlement.ts:89-93`) — error channel `never`. So a `retryable` return succeeds, the batch is acked, and the event is gone.

`attempt` is genuinely pinned: `src/Workers/Settlement.ts:152` `send.send({ event, attempt: 1 })` is the only enqueue in the tree (the `settleNow` RPC at `:168` is the test harness). Nothing re-enqueues with `attempt + 1`, so `attempt < MAX_ATTEMPTS` at `src/Domain/Settlement.ts:204` is always true and the `dead` row at `:205` is unreachable in production — but that is secondary, since the message is acked before either matters.

The failure scenario checks out. `src/Services/PaymentsStripe.ts:302-322` returns `sessionId: null, orderId: null, paymentIntentId: intent` for every `charge.*` event, so `byIntent` (`src/Domain/Settlement.ts:185-194`) is the only lookup. Orders with NULL `payment_intent_id` are reachable two ways I verified: the heal path at `src/Domain/Reconcile.ts:141-148` writes only `status`/`paymentStatus`, and the `describesOurSession === false` path at `src/Domain/Settlement.ts:320-322,333` produces `collected = {}`. For such an order `!order` is true, `retryable` returns BEFORE any `record(...)` runs, the message is acked, and no `payment_event` row exists — the dispute leaves no trace and the order stays `status='paid'` and shippable. The reconcile sweep does not cover reversals at all (`src/Domain/Reconcile.ts` only queries `status='pending'`), so nothing recovers it. Contradicts `src/Domain/Settlement.ts:10-11,27-29` and `src/Workers/Settlement.ts:95-98`. High stands.


### F7. Order detail hardcodes shipping country to "CA", discarding stored ship_country for every US order

**MEDIUM** · `src/Domain/Orders.ts:72` · lens `?` · reviewer confidence `high`

**Defect.** `customer_order.ship_country` is a real column written with the buyer's actual destination (`"CA"` or `"US"`) at checkout and overwritten with Stripe's collected country at settlement, but `toAddress` ignores the column and emits the literal `country: "CA"` — and the RPC wire schema pins it to `Schema.Literal("CA")`, so a US address is not even representable in the operator's order DTO.

**Failure.** A buyer in Austin selects destination `US` on the storefront. `Checkout.placeOrder` writes `ship_country: 'US'` (Checkout.ts:117). Stripe's `allowed_countries: ['US']` collects a Texas address; settlement copies `shipCountry: 'US'` and the address fields onto the row (Settlement.ts:336, 355-365). The operator then calls `getOrder("SO-XXXXXXXX")`. `loadOrder` returns `shipping: toAddress(row)` = `{ name: "…", line1: "…", city: "Austin", region: "TX", postal: "78701", country: "CA" }` — the stored `'US'` is dropped on the floor. Any fulfilment UI or label generator that reads `shipping` (the field named "where it ships", carrying the full address block) prints "Austin, TX 78701, Canada". The parcel is dispatched with a Canadian destination for a US address: it is returned or lost, and the store eats postage plus a refund. The single DTO is internally contradictory — `shipCountry: "US"` sits three fields above `shipping.country: "CA"` — so the reader has no signal which one to trust.

**Independent verification.** The literal is real and US is a genuinely reachable destination, so I could not refute it. Orders.ts:64-75 builds the address from row.shipName/Line1/City/Region/Postal and emits `country: "CA"` (Orders.ts:72); `row.shipCountry` is only used for the separate top-level field at Orders.ts:106. The wire type pins it too — Rpc.ts:123 `country: Schema.Literal("CA")`, Contracts.ts:155-164 'Canada only: country is a compile-time literal, not a column read'. Against that, US is first-class everywhere else: Storefront.rpc.ts:38 `Destination = Schema.Literals(["CA","US"])`, Workers/Catalog.ts:70-79 passes it through unvalidated-against-CA, Checkout.ts:117 writes `shipCountry: input.destination`, StripeConfig.ts:76/90-96 ships a US rate, PaymentsStripe.ts:239 sets `allowed_countries: [input.destination]`, and Settlement.ts:336 copies Stripe's collected country back. So a US order really does produce a DTO whose `shipCountry: "US"` contradicts `shipping.country: "CA"`. I drop severity from high to medium: the finder's parcel-misdispatch scenario is downstream speculation — there is no fulfilment UI or label generator in this repo, and the correct value sits in the same DTO three fields up, so an integrator has the truth available. It is a wrong value in a published contract, not a demonstrated loss.


### F8. Queue consumer ACKs `retryable` settlements — the event is dropped, never retried, never recorded

**MEDIUM** · `src/Workers/Settlement.ts:107` · lens `?` · reviewer confidence `high`

**Defect.** `settle` reports `retryable` as a SUCCESS VALUE on an error channel typed `never`, so the queue handler always succeeds and alchemy's EventSource acks every message in the batch. The `retryable` outcome therefore never retries anything — contradicting the comment directly above it — and because `settle` writes no `payment_event` row on that path, the event vanishes with zero evidence.

**Failure.** A `charge.refunded` arrives for an order whose `payment_intent_id` is NULL. That is a reachable state: `Reconcile.sweep`'s heal branch (Reconcile.ts:141-148) sets only `status`/`paymentStatus` and never writes `paymentIntentId`, and `Settlement.settle` writes it only when `describesOurSession` (Settlement.ts:320-335). `settle` then matches no order by session, order id, or intent; `attempt` (1) < `MAX_ATTEMPTS` (5), so it returns `{ outcome: "retryable", orderNumber: null }` — a plain success. `Effect.forEach(..., { discard: true })` discards it, the handler Effect succeeds, and alchemy calls `msg.ack()` on every message in the batch. No `payment_event` row exists (so a hypothetical redelivery would not even be a `duplicate`), the customer_order stays `status = 'paid' / paymentStatus = 'paid'`, and an operator ships goods for money Stripe has already returned to the buyer. Same loss shape for `charge.dispute.created`.

**Independent verification.** MECHANISM CONFIRMED. `settle` is typed `Effect.fn.Return<Settlement, never, Database>` (src/Domain/Settlement.ts:93) and returns `{ outcome: 'retryable' }` as a SUCCESS value (src/Domain/Settlement.ts:204). The handler at src/Workers/Settlement.ts:103-112 runs `Effect.forEach(..., { discard: true })` and never inspects the outcome, so the process Effect always succeeds. alchemy acks unconditionally on success — node_modules/alchemy/src/Cloudflare/Queues/EventSource.ts:239-243 (`Effect.tap(() => Effect.sync(() => { for (const msg of batch.messages) msg.ack(); }))`), with `msg.retry()` only on the `Effect.onError` branch at 245-256. No per-message ack/retry exists in the handler. So `retryable` never retries, directly contradicting the comments at src/Workers/Settlement.ts:94-98 and src/Domain/Settlement.ts:9-12. Real prose-vs-code gap.

The refund join genuinely dies with it: Settlement.ts:185-194 is the only path a charge event has, it matches on `paymentIntentId`, and a null column never matches, so the event falls through to `dead` with `orderId: null` (Settlement.ts:203-207) while the order stays `paid` and shippable (`fulfillOrder` gates on `status`, Orders.ts:262).

### O6. setPreorderCap's cap_below_claimed check is a stale read; a concurrent claim aborts the audited batch

**LOW** · `src/Domain/Catalog.ts:696` · lens `?` · reviewer confidence `high`

**Defect.** `setPreorderCap` compares the requested cap against a `preorder_claimed` value read in a separate query from the batch that writes the cap, and the UPDATE carries no guard, so a claim landing in between makes the write violate `preorder_claimed_within_cap` and abort the whole audited batch.

**Failure.** Product P has `preorder_cap = 200`, `preorder_claimed = 148`. An operator closes the run down to 148 (`setPreorderCap({productId: P, cap: 148})`). The SELECT at line 686 reads `claimed = 148`, so the `input.cap < current.claimed` test passes and the core returns an unguarded `UPDATE product SET preorder_cap = 148`. Before that batch commits, a checkout's `runGuardStatement` fires against the still-200 cap and claims 3 places: `preorder_claimed = 151`. The operator's batch — which `Audit.command` builds as `[...outcome.statements, <store_operator_event insert>]` and commits under `Effect.orDie` — now writes `preorder_cap = 148` with `preorder_claimed = 151`, violating `CHECK(preorder_cap IS NULL OR preorder_claimed <= preorder_cap)`. Unlike a zero-row UPDATE, a constraint violation is a statement ERROR and aborts the entire D1 batch, so the audit row is lost too and the operator receives a 500 defect instead of the `cap_below_claimed` domain error the function was written to return. The same window makes the reported `remaining` value wrong on the success path.

**Independent verification.** The race is real but the consequence is much smaller than claimed. Catalog.ts reads `preorder_claimed` in its own SELECT, tests `input.cap < current.claimed`, and returns an UPDATE whose WHERE is only `eq(product.id, ...)` — no `preorder_claimed <= cap` predicate, unlike runGuardStatement (Reservations.ts:246-252) and adjustStock (Catalog.ts, `stock + delta >= 0` in SQL). The CHECK exists and is deployed (Schema.ts:110-113, migrations/20260803012436_sticky_killer_shrike/migration.sql:112), and Audit.command commits under `Effect.orDie` (Services/Audit.ts:128-146), so a claim landing in the window does turn a domain error into a 500. However: the CHECK fires, so D1 rolls the whole batch back — the cap is NOT lowered below claimed, `preorder_cap`/`preorder_claimed` stay consistent, and because no operator_event row is written the idempotency key is unconsumed, so an immediate retry re-reads claimed=151 and returns the proper `cap_below_claimed`. There is no data corruption, no money loss, and no oversell — the schema constraint the finder cites as the victim is in fact what saves it. The window is the few ms between the SELECT and the batch, and it only bites when an operator shrinks a cap to within a few units of claimed at the exact moment a checkout claims. Genuine but low: a spurious 500 on a self-healing operator path, plus a possibly-stale `remaining` in the success response.


### O7. `/media/:id` serves any image row with no publication check, and marks it immutable for a year

**LOW** · `src/Workers/Catalog.ts:159` · lens `?` · reviewer confidence `high`

**Defect.** `Media.openMedia` resolves a media id straight to bytes with `where(eq(productImage.id, mediaId))` and nothing else — no join to `product.status`, no join to `product_release_image`, no check that the owning product has an active release — while the file header claims "Everything it serves comes from a product's ACTIVE RELEASE" and the route comment claims "access stays revocable".

**Failure.** Operator publishes product P, its image ids become public via `/products/<slug>`. Operator later calls `setProductStatus(P, "unavailable")` — which the code documents as "a published product pulled from sale and must not appear" — or publishes a new release that drops an image. `/products` and `/products/<slug>` correctly stop serving P, but `GET /media/<id>` continues to return the bytes to any anonymous caller indefinitely, because the route consults only the `product_image` row, which neither operation touches. The same holds for images on `draft` and `archived` products and on superseded releases. The `cache-control: public, max-age=31536000, immutable` header then keeps the withdrawn asset alive in browser and edge caches for a year after even a genuine `deleteProductMedia`, which is the opposite of the revocability the comment claims the proxy buys.

**Independent verification.** The code claim holds and it is a genuine prose-vs-code gap. Media.ts:127-134 resolves bytes with `where(eq(productImage.id, mediaId))` and nothing else — no join to `product.status`, no join to `product_release_image`, no active-release predicate. The only other gate is R2 object existence (Media.ts:138-141). Meanwhile Catalog.ts:17-18 asserts "Everything it serves comes from a product's ACTIVE RELEASE" and Catalog.ts:154-158 asserts "access stays revocable", and Storefront.ts:55 makes a point of the INNER join being "fail-closed" — so a reader will reasonably believe `/media/:id` is gated the same way the two product routes are. It is not. `setProductStatus(P, "unavailable")` (Catalog.ts:~500+) writes only `product.status`, and publishing a new release does not touch `product_image`, so bytes stay served in both cases.

I am downgrading from medium to low on exploitability. Media ids are ULIDs with 16 base32 random characters (Ids.ts:26, 52-58, 84-86) — ~80 bits — so there is no enumeration path. Reaching a withdrawn image requires having already held the URL while it was public, meaning the practical exposure is "a link I already had keeps working after the product is pulled", not a fresh disclosure. Draft/archived product images are not reachable at all in practice for the same reason.

The cache-control sub-claim is the weakest part and I would drop it: `max-age=31536000, immutable` is correct given ids are never reused, and `deleteProductMedia` does remove the R2 object (Deletion.ts:842 `onCommitted: blobs.delete([derived.storageKey])`), so the origin does revoke. Downstream cache retention is normal HTTP behaviour, not a defect in this code.

Worth reporting because the comment is load-bearing and false, but as a low-severity gap, not a data leak.


### O8. Public read routes return the raw Effect cause string to anonymous callers

**LOW** · `src/Workers/Catalog.ts:180` · lens `?` · reviewer confidence `high`

**Defect.** The catch-all around Catalog's public GET routes serialises the internal failure cause into the response body (`String(cause).slice(0, 600)`), so infrastructure detail — D1 error text including SQL fragments, and Effect's stack trace with source file paths and span names — is returned verbatim to unauthenticated internet callers.

**Failure.** `Services/Database.ts:107` defines `query` as `Effect.promise(...)`, which turns any D1 rejection into a defect rather than a typed failure, and the storefront reads use it exclusively. Any D1-side error on `GET /products`, `GET /products/<slug>` or `GET /media/<id>` — e.g. `listActiveProducts` building `inArray(productReleaseImage.releaseId, rows.map(...))`, one bound parameter per active release, against D1's 100-bound-parameter-per-query limit once the catalogue exceeds 100 active products; or a transient `D1_ERROR: Network connection lost` under load — is caught here and echoed. The anonymous caller receives `{"error":"...D1_ERROR: too many SQL variables ... at Storefront.listActiveProducts (file:///.../src/Domain/Storefront.ts:44) ..."}` with HTTP 500. No other worker on a browser-reachable path does this, and Commerce/Settlement failures never reach a client this way.

**Independent verification.** The mechanism is real: Catalog.ts:178-183 wraps the three anonymous GET routes in `Effect.catchCause((cause) => HttpServerResponse.json({ error: String(cause).slice(0, 600) }, { status: 500 }))`, and Database.ts:107-108 defines `query` as `Effect.promise`, so any D1 rejection becomes a defect that lands in that catch and is echoed to the caller. Storefront.ts and Media.ts use `query` exclusively, so the path is reachable.

But the evidence section materially overstates what leaks, and the author will notice. I traced the rendering: `String(cause)` hits `CauseImpl.toString()` (effect/src/internal/core.ts:159-161) → `Cause(${format(this.reasons)})`, each reason being `Die(${format(this.defect)})` (core.ts:297-299). `format` (effect/src/Formatter.ts:149-161) calls the value's own `toString`, which for an `Error` is `Error.prototype.toString` — name and message only. There is no stack, no `file:///.../src/Domain/Storefront.ts:44`, and no span name in the output. The actual body is roughly `{"error":"Cause(Die(Error: D1_ERROR: ...))"}` — a D1 error string and nothing more. The quoted sample response in the finding cannot be produced.

So this is a real but low-severity infrastructure-detail disclosure (D1 error text, occasionally a column or table name), not a stack-trace/source-path leak. The D1 100-bound-parameter angle at Storefront.ts:62-78 is a separate latent bug (the `inArray` over every active release), not evidence for this one, and citing it here muddies the report. Worth a one-line fix — log the cause, return a static body — but it should be filed as low.

**Defect.** `publishProduct` selects ALL `product_image` rows for the product with no role filter and copies each into `product_release_image`, and `Storefront.getActiveProductBySlug` returns every release image with no role filter — so the `evidence` role, the one member of the three-value role domain that is not a display role, is served to anonymous shoppers. **HIGH** · `src/Workers/Catalog.ts:52` · lens `?` · reviewer confidence `high`
